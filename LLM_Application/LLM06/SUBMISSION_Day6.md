**설명**
- **6.3 / 6.4 (인증)** — API Key가 없거나(`X-API-Key` 헤더 누락) 잘못되면 `Depends(verify_api_key)`가 **401**로 차단합니다. 엔드포인트 본문은 실행되지 않습니다.
- **6.5 (정상)** — 올바른 키(`test-key-001`) + MNIST 이미지를 보내면 **200**, 응답에 `label`(예측), `confidence`, 인증된 `user`("사용자A")가 담깁니다.
- **6.6 (안전장치)** — `.txt` 파일(`text/plain`)은 `image_utils`의 타입 검증에서 **400**으로 차단됩니다.
- **6.7 (연속)** — MNIST 5장 모두 정답과 일치(확신도 ~1.0).
- **6.8 (Swagger UI)** — `/docs`가 **200**으로 제공되며, 자동 생성된 OpenAPI 문서에 `/predict/image` 엔드포인트가 노출됩니다.

### 6.8 Swagger UI 테스트 (브라우저)

```
1. 브라우저에서 http://localhost:8000/docs 접속  → Swagger UI 표시 (HTTP 200 확인됨)
2. POST /predict/image → Try it out
3. x-api-key 입력란에 test-key-001 입력
4. Choose File → 숫자 이미지(PNG/JPEG) 선택
5. Execute → {"success": true, "label": "...", "confidence": ..., "user": "사용자A"} 확인
```

> `Header()`로 정의한 `x_api_key` 파라미터가 Swagger UI에 `x-api-key` 입력란으로 나타납니다
> (언더스코어 `_` → 하이픈 `-` 자동 변환). 위 6.5 결과가 이 Swagger 호출과 동일한 요청입니다.

> ⚠️ **참고**: 위 6.3~6.8은 `requests`로 자동 수행한 실제 결과입니다. 6.8의 **브라우저 화면 캡처**가 별도로 필요하면, 서버 실행 후 `http://localhost:8000/docs`에서 위 절차대로 캡처해 첨부하면 됩니다.

## 2. 각 섹션 체크포인트 답변

### 섹션 1 — API 보안의 필요성
1. **인증 없는 API가 위험한 이유 (2가지+)** — ① **서버 과부하/다운**: 누구나 무제한 호출(`while True`)로 CPU/GPU를 소진시켜 정상 사용자가 못 씀(DoS). ② **비용 폭탄**: 클라우드 GPU 사용량이 치솟아 요금 폭증. (그 외 ③ 입출력 수집을 통한 **모델 도용**, ④ 누가 호출했는지 **추적 불가**)
2. **API Key가 ML 추론 API에 적합한 이유** — 사용자 로그인이 필요 없고, **키 하나로 인증과 사용량 추적**을 동시에 할 수 있어 간단합니다. OpenAI·Anthropic·Hugging Face 등 대부분의 ML API가 이 방식을 씁니다.

### 섹션 2 — API Key 인증
1. **`Header(None)`에서 `None`이 들어오는 상황** — 요청에 `X-API-Key` 헤더가 **아예 없을 때**.
2. **`Depends(verify_api_key)`를 추가하면 흐름 변화** — 엔드포인트 함수 실행 **전에** `verify_api_key()`를 먼저 실행. 성공하면 반환값(사용자명)이 `user`에 주입되고, 실패하면 `HTTPException(401)`이 발생해 **엔드포인트는 실행되지 않고 401 반환**.
3. **401의 의미** — Unauthorized. 인증이 필요한데 자격이 없거나(키 누락) 유효하지 않음.

### 섹션 4 — 파일 업로드 안전장치
1. **`UploadFile` vs Base64 핵심 차이** — UploadFile은 파일을 **multipart로 직접 전송**(Swagger에 파일 선택 버튼 자동 생성), Base64는 파일을 **문자열로 인코딩해 JSON에 담아** 전송(다른 JSON 데이터와 함께 보낼 때 유리).
2. **`content_type`으로 타입 검증하는 이유** — `text/plain` 같은 명백히 엉뚱한 형식을 **싸게 1차 차단**하기 위함. (단 클라이언트가 위조 가능 → 위장 파일의 최종 차단은 PIL 디코딩 단계가 담당)
3. **파일 크기를 제한하지 않으면** — 100MB 같은 거대 파일이 서버 **메모리·처리 부하**를 일으켜 다른 사용자에게 영향을 주고 응답이 지연되거나 서버가 다운될 수 있음.

### 섹션 6 — Day 6 최종 체크포인트
- **Q1. 인증 없으면 위험(2+)** → 서버 과부하(DoS), GPU 비용 폭탄, 모델 도용, 추적 불가 중 2가지 이상.
- **Q2. `Depends(verify_api_key)`가 실행 전 하는 일** → 인증 함수를 먼저 실행해 키를 검증하고, 실패 시 401로 요청을 차단(본문 미실행).
- **Q3. UploadFile이 Base64보다 편리한 점** → 파일을 직접 보내고 Swagger에 파일 선택 버튼이 자동 생성되어 인코딩이 필요 없음.
- **Q4. 파일 크기 제한이 없으면** → 거대 파일로 메모리/처리 부하 → 서비스 마비 위험.
- **Q5. 28×28 그레이스케일로 변환하는 이유** → MNIST 모델의 입력 형식(**1채널 28×28**)에 맞춰야 추론이 가능하기 때문.

## 3. 회고 (참고)

- **배운 점**: `Depends()` 의존성 주입으로 인증을 한 줄로 적용하는 패턴, `UploadFile`로 비정형(이미지) 데이터를 받고 **타입→크기→디코딩→리사이즈** 순으로 안전하게 검증하는 흐름을 익혔습니다.
- **디버깅**: 테스트 중 모든 요청이 400(`body 파싱 에러`)으로 나와 혼란이 있었는데, 원인은 **이전 서버가 포트 8000을 점유**해 새 서버가 못 뜨고 요청이 엉뚱한 서버로 간 것이었습니다. 포트를 정리하고 재기동하니 정상 동작했습니다. (`systematic-debugging`)
- **개선점**: API Key 하드코딩 → 환경변수/시크릿 매니저, 크기 제한을 "다 받은 뒤"가 아니라 리버스 프록시/스트리밍으로 사전 차단, 요청 rate limit 추가.
