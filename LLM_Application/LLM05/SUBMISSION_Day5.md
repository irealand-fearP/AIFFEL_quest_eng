## 2. 각 섹션 체크포인트 답변

### 섹션 1 — 프로젝트 개요
1. **입력/출력?** 입력은 8개 정형 피처(중위소득·연식·방수·침실수·인구·거주인원·위도·경도), 출력은 중위 주택가격($100,000 단위) — **회귀**.
2. **MNIST와 데이터 형태 차이?** MNIST는 28×28 **이미지 분류**, 이번은 8개 숫자 피처의 **정형 데이터 회귀**. 전처리·스키마·UI가 모두 다름.
3. **새 파일 3개?** `housing_model.py`(모델+추론), `housing_schemas.py`(API 스키마), `housing_api.py`(FastAPI 서버).

### 섹션 2 — 모델 준비
1. **학습 통계로 테스트를 정규화하는 이유?** 배포 시 들어올 새 데이터의 통계를 미리 알 수 없으므로, 학습 때 계산한 mean/std를 그대로 적용해 일관성을 유지. 테스트 데이터는 "미래 데이터"를 시뮬레이션함.
2. **함께 저장해야 하는 것?** 전처리 파라미터(`mean`, `std`, `feature_names`). 없으면 배포 환경에서 정규화를 못 해 잘못된 예측이 나옴.
3. **`feature_names` 순서로 배열하는 이유?** 모델은 학습 때의 피처 순서대로 입력을 기대. 사용자가 dict를 임의 순서로 줄 수 있어, 저장된 순서로 정렬해야 정확한 추론이 됨.

### 섹션 3 — FastAPI 백엔드
1. **`Latitude`에 `ge=32, le=42` 제한 이유?** 캘리포니아의 실제 위도 범위. 범위 밖 입력을 422로 차단해 엉뚱한 추론을 막음.
2. **`request.model_dump()` 역할?** Pydantic 요청 모델 객체를 일반 `dict`로 변환 (추론 함수 `predict(features: dict)`에 넘기기 위함).
3. **`run_in_executor`를 안 쓰면?** 추론(CPU 작업)이 이벤트 루프를 막아, 동시 요청이 순차 처리되고 서버 응답성이 크게 떨어짐.

### 섹션 4 — Streamlit 프론트엔드
1. **MNIST 대시보드와 입력 차이?** MNIST는 이미지 업로드/그리기, 이번은 숫자 입력 폼(`st.number_input`) 8개.
2. **`min_value`/`max_value` 설정 이유?** 잘못된 범위 입력을 UI 단계에서 미리 막아 사용자 실수 방지 (+ 서버 검증과 이중 안전장치).
3. **키 이름이 스키마 필드와 일치해야 하는 이유?** FastAPI/Pydantic이 **필드 이름으로 매칭·검증**하므로, 이름이 다르면 검증 실패(422)나 값 누락이 발생.

### 섹션 5 — 통합 테스트
- 정상/에러/동시/헬스체크 4종 테스트 전부 통과 (위 실행 내역 참고). 에러는 모두 422로 처리되고 서버가 죽지 않음을 확인.

### 섹션 6 / Day 5 최종 체크포인트
- **Q1.** 전처리 파라미터를 모델과 함께 저장하는 이유 → 배포 환경에서 동일한 정규화를 재현하기 위함(없으면 오예측).
- **Q2.** `Latitude` ge=32,le=42 이유 → 캘리포니아 위도 범위 밖 입력 차단.
- **Q3.** Streamlit 입력 이름이 스키마 필드와 일치해야 하는 이유 → Pydantic이 이름으로 매칭/검증하기 때문.
- **Q4.** `run_in_executor` 제거 시 → 추론이 이벤트 루프를 블로킹해 동시 처리 성능 저하.
- **Q5.** MNIST 프로젝트와 가장 큰 차이 → **데이터 유형**(이미지 분류 → 정형 회귀)과 그에 따른 전처리·스키마·UI 전반의 차이.

## 3. 프로젝트 회고

**배운 점**
- Day 1~4의 조각들(venv·직렬화·FastAPI·Streamlit)을 **하나의 엔드투엔드 서비스**로 통합하는 경험을 했습니다.
- 모델 가중치만이 아니라 **전처리 파라미터를 함께 배포**해야 한다는 점을 실제 코드로 체득했습니다.
- 비동기(`async`) + `ThreadPoolExecutor`로 **동시 요청을 막힘 없이 처리**하는 패턴을 확인했습니다.

**어려웠던 점 / 디버깅**
- 서버 코드가 Day 2~4에서 만든 모듈(`logger_config`/`error_handlers`/`middleware`)에 의존해, 해당 모듈을 **최소 동작 버전으로 재구성**해야 했습니다.
- 통합 테스트의 "잘못된 포맷(bytes)" 케이스에서 **검증 오류의 원본 입력이 bytes라 JSON 직렬화가 실패**하는 버그를 만났고, 응답에 `type/loc/msg`만 담도록 고쳐 해결했습니다 → 이후 모든 에러가 422로 안정 처리.

**개선할 수 있는 점**
- 모델 성능(현재 테스트 MAE ≈ $39k) — 더 깊은 네트워크/피처 엔지니어링/정규화 기법 적용.
- 검증 에러 메시지 한글화, 모델 버전 관리, Docker 컨테이너화(다음 Day/ MLOps 단계).
