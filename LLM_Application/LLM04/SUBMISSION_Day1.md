## 2. 각 섹션 체크포인트 답변

### 섹션 1 — 들어가며

**Q1. `.pth` 파일만 전달했을 때, 상대방이 모델을 바로 사용할 수 없는 이유는?**
`.pth`에는 **가중치(state_dict)만** 들어 있고, 모델 구조(클래스 정의)와 실행 환경(파이썬·라이브러리 버전), 전처리 코드는 들어 있지 않습니다. 받는 사람이 동일한 모델 클래스 코드와 같은 버전의 PyTorch가 없으면 불러오거나 추론할 수 없습니다.

**Q2. 모델 학습과 배포의 핵심 차이를 한 문장으로?**
학습은 "좋은 모델(가중치)을 만드는 것"이고, 배포는 "그 모델을 환경에 상관없이 누구나 쓸 수 있는 서비스로 꺼내놓는 것"입니다.

**Q3. 사용자와 서버가 소통하는 방식은?**
**HTTP 기반의 REST API**입니다. 약속된 형식(주로 JSON)으로 요청하고 응답받습니다.

### 섹션 2 — 환경 세팅

**Q1. 가상환경 없이 `pip install`을 하면 어디에 설치되고 왜 문제인가?**
**시스템(전역) 파이썬**에 설치됩니다. 여러 프로젝트가 같은 패키지의 다른 버전을 요구하면 충돌이 나고, 한 프로젝트의 설치가 다른 프로젝트를 깨뜨릴 수 있어 환경 격리·재현이 불가능합니다.

**Q2. `pip freeze` 파일과 직접 작성한 `requirements.txt`의 차이는?**
`pip freeze`는 **하위 의존성까지 모든 패키지를 정확한 버전(`==`)으로** 기록해 정밀 재현에 유리합니다(가독성은 낮음). 직접 작성한 것은 사람이 관리하는 **핵심 패키지만** 적어 읽기 쉽습니다. 실무에서는 둘을 병행합니다.

**Q3. 동료에게 전달할 때 `.venv` 폴더 대신 무엇을 공유하나?**
**`requirements.txt`(의존성 목록)** 를 공유합니다. `.venv`는 용량이 크고 OS에 종속적이라 그대로 전달하지 않습니다.

### 섹션 3 — RESTful API

**Q1. 모델 추론 요청에 GET이 아닌 POST를 쓰는 이유는?**
입력 데이터를 **요청 본문(body)에 담아 보내야** 하기 때문입니다. GET은 본문이 없고 URL로만 정보를 전달합니다.

**Q2. 상태 코드 `422`는 어떤 상황에서 발생하나?**
요청은 도달했지만 **데이터 검증에 실패**했을 때(필수 필드 누락, 타입 불일치 등). FastAPI/Pydantic이 입력 검증 실패 시 반환합니다.

**Q3. `requests.post(url, json=data)`에서 `json=`은 내부적으로 무슨 일을 하나?**
`data`(dict)를 **JSON 문자열로 직렬화**하고, `Content-Type: application/json` **헤더를 자동 설정**해 전송합니다.

**Q4. Python의 `True`는 JSON에서 어떻게 표현되나?**
소문자 **`true`** 로 표현됩니다.

### 섹션 4 — 모델 직렬화

**Q1. `state_dict`(.pth) 로드 시 모델 클래스 정의가 필요한 이유는?**
`.pth`에는 **가중치(숫자)만** 저장되고 구조(레이어 연결)는 없어서, **같은 구조의 클래스를 먼저 생성**한 뒤 거기에 가중치를 끼워 넣어야 하기 때문입니다.

**Q2. `torch.jit.trace`와 `torch.jit.script`는 각각 언제 쓰나?**
- `trace`: 더미 입력을 한 번 흘려 **연산 경로를 기록**. 분기(if/else)가 없는 모델에 안정적.
- `script`: 파이썬 코드를 분석해 컴파일하여 **if/else·for 등 동적 로직도 변환**. 단, 지원되지 않는 문법은 에러.

**Q3. ONNX의 가장 큰 장점과 선택 시점은?**
**프레임워크·언어에 독립적**(어디서든 실행)이며 ONNX Runtime·TensorRT 등 하드웨어 최적화 엔진과 호환됩니다. **추론 속도·이식성이 중요한 프로덕션**에서 선택합니다.

**Q4. `dynamic_axes`를 지정하지 않으면 어떤 문제가 생기나?**
`batch_size`가 export 당시 크기(예: 1)로 **고정**되어, 배포 시 여러 입력을 **배치로 한 번에 처리할 수 없습니다.**

### 섹션 5 — 마치며 (종합 Q1~Q10)

**Q1. 학습과 배포의 핵심 차이(한 문장)?** → 학습은 좋은 모델을 만드는 것, 배포는 그 모델을 환경 독립적인 서비스로 꺼내놓는 것.
**Q2. "내 컴퓨터에서는 되는데" 문제의 근본 원인?** → 모델이 특정 환경(라이브러리 버전·구조 코드·OS)에 **갇혀 있어 환경이 공유되지 않기** 때문.
**Q3. 가상환경을 안 쓰면 생기는 문제?** → 전역 설치로 프로젝트 간 **버전 충돌**, 환경 **재현 불가**.
**Q4. `pip freeze` vs `requirements.txt` 용도 차이?** → freeze는 전체 의존성 정밀 재현용, requirements.txt는 사람이 관리하는 핵심 목록.
**Q5. 추론에 POST를 쓰는 이유?** → 입력 데이터를 본문에 담아 보내야 하므로.
**Q6. 상태 코드 200·400·500의 의미?** → 200 성공, 400 클라이언트(요청) 오류, 500 서버 내부 오류.
**Q7. `state_dict`가 모델 클래스 정의를 필요로 하는 이유?** → 가중치만 저장되고 구조는 저장되지 않으므로.
**Q8. ONNX의 장점과 사용 시점?** → 프레임워크·언어 독립 + 최적화 런타임 호환, 추론 속도·이식성이 중요할 때.
**Q9. 저장 전 `model.eval()`을 호출해야 하는 이유?** → **Dropout·BatchNorm이 학습/추론 모드에서 동작이 달라서**, 추론용 저장 시 eval()로 고정해야 일관된 결과가 나옵니다.
**Q10. `predict()`를 별도 모듈로 분리한 이유?** → FastAPI 등 다른 코드에서 **재사용·import**가 쉽고, 추론 로직과 서버 코드를 분리해 **유지보수·테스트**가 쉬워지기 때문.
